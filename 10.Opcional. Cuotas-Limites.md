# 10. Laboratorio Opcional: Cuotas y Límites <!-- omit in toc -->

Este laboratorio tiene como objetivo aprender a controlar el consumo de recursos en un clúster de Kubernetes utilizando dos herramientas clave:
1. **ResourceQuota (Cuotas):** Funciona como un **presupuesto para todo el Namespace**. Limita la cantidad total de recursos (CPU, memoria, pods, etc.) que todos los usuarios y aplicaciones pueden consumir en conjunto en ese namespace.
2. **LimitRange (Rangos de límite):** Funciona como una **regla de fábrica para contenedores individuales**. Definir valores por defecto (en caso de omitirse en la especificación del pod) y límites mínimos/máximos de recursos que cada contenedor puede solicitar.

> [!NOTE]
> **Documentación de referencia:**
> * [Documentación de Limit Ranges](https://kubernetes.io/docs/concepts/policy/limit-range/)
> * [Documentación de Resource Quotas](https://kubernetes.io/docs/concepts/policy/resource-quotas/)
> * [Prácticas recomendadas: Resource Requests and Limits](https://cloud.google.com/blog/products/containers-kubernetes/kubernetes-best-practices-resource-requests-and-limits)

### Conceptos clave: Request y Limit

Para gestionar los recursos asignados a cada contenedor en Kubernetes, se configuran dos parámetros fundamentales:

* **Request (Solicitud):** Representa el **recurso mínimo garantizado**. Es la cantidad de CPU o memoria que Kubernetes reserva exclusivamente para que el contenedor pueda iniciar y ejecutarse de manera estable. El planificador de Kubernetes utiliza este valor para seleccionar un nodo que disponga de dicha capacidad libre.
* **Limit (Límite):** Representa el **recurso máximo permitido**. Es el límite superior de CPU o memoria que el contenedor tiene autorizado consumir. Si un contenedor excede su límite de memoria, es finalizado por falta de recursos (error `OOMKilled`). Si excede su límite de CPU, su rendimiento se restringe (proceso de *throttling*), pero no se detiene.

## Requisitos previos
* Un clúster de Kubernetes activo.
* La herramienta `kubectl` configurada para interactuar con el clúster.

---

## Paso 1: Configurar el entorno (Namespace)

Para no interferir con otros proyectos, trabajar en un namespace llamado `dev`.

1. **Crear el namespace `dev` (si no existe):**
   ```bash
   kubectl create namespace dev
   ```

2. **Establecer `dev` como el namespace predeterminado:**
   De esta forma, se evita tener que escribir `-n dev` al final de cada comando.
   ```bash
   # Si se tiene instalado kubens:
   kubens dev

   # O usando kubectl directamente:
   kubectl config set-context --current --namespace=dev
   ```

---

## Parte 1: ResourceQuota (El presupuesto del Namespace)

### Paso 2: Crear el archivo de cuota (`quota.yaml`)
Crear un archivo llamado `quota.yaml` e introducir el siguiente contenido. 

Este archivo define los límites máximos permitidos en todo el namespace `dev`:

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: dev-quota
  namespace: dev
spec:
  hard:
    # Límites de objetos
    pods: "10"                      # Máximo 10 Pods en total
    persistentvolumeclaims: "4"     # Máximo 4 solicitudes de almacenamiento (PVC)
    services: "10"                  # Máximo 10 servicios
    services.loadbalancers: "2"     # Máximo 2 servicios de tipo LoadBalancer
    secrets: "10"                   # Máximo 10 secretos

    # Límites de CPU y Memoria combinados de todos los Pods activos
    requests.cpu: "250m"            # Mínimo CPU reservado total: 250 milicores (1/4 de core)
    requests.memory: 100Mi          # Mínima memoria reservada total: 100 Megabytes
    requests.storage: 1000Mi        # Máximo almacenamiento total: 1000 Megabytes
    limits.cpu: "500m"              # Máximo uso de CPU total: 500 milicores (1/2 core)
    limits.memory: 500Mi            # Máxima memoria total: 500 Megabytes
```

> [!NOTE]
> **Unidades de medida en Kubernetes:**
> * **CPU (`m` / milicores):** `1000m` equivale a 1 CPU Core físico o virtual. `250m` es 0.25 Cores (un cuarto de CPU).
> * **Memoria (`Mi` / Mebibytes):** Medida de memoria RAM. `100Mi` es aproximadamente 104 Megabytes.

### Paso 3: Aplicar la cuota
Ejecutar el siguiente comando para aplicar la cuota en el clúster:
```bash
kubectl apply -f quota.yaml
```
* **Resultado esperado:**
  ```text
  resourcequota/dev-quota created
  ```

### Paso 4: Inspeccionar la cuota
Para verificar el estado actual del presupuesto y el espacio disponible:
```bash
kubectl describe quota dev-quota
```
* **Aspectos a observar:**
  * La columna **Hard** muestra el límite total definido.
  * La columna **Used** muestra el consumo actual (debería mostrar valor 0 si el namespace está vacío).

---

### Paso 5: Poner a prueba la cuota (Caso de error)
Intentar crear un Pod que solicite más recursos de los permitidos por la cuota.

1. Crear un archivo llamado `pod-quota-dev.yaml` con el siguiente contenido:
   ```yaml
   apiVersion: v1
   kind: Pod
   metadata:
     name: errorapp
     namespace: dev
     labels:
       app: errorapp
   spec:
     containers:
     - name: errorapp
       image: "nginx:latest"
       resources:
         limits:
           cpu: 250m
           memory: 500Mi
         requests:
           cpu: 250m
           memory: 500Mi  # <--- Solicitud de 500Mi supera la cuota máxima permitida (requests.memory) de 100Mi.
   ```

2. Intentar aplicar este Pod:
   ```bash
   kubectl apply -f pod-quota-dev.yaml
   ```

* **Resultado esperado (Error):**
  El comando debe ser rechazado con un mensaje similar al siguiente:
  ```text
  Error from server (Forbidden): error when creating "pod-quota-dev.yaml": pods "errorapp" is forbidden: exceeded quota: dev-quota, requested: requests.memory=500Mi, used: requests.memory=0, limited: requests.memory=100Mi
  ```

> [!NOTE]
> **Explicación:** Se recibe un error de tipo "Forbidden" (Prohibido) debido a que se solicitaron 500Mi de memoria, lo cual supera el límite de 100Mi permitido por la cuota del namespace.

---

### Paso 6: Corregir y volver a intentar
Ajustar el Pod para consumir recursos dentro del límite permitido.

1. Abrir `pod-quota-dev.yaml` y modificar la sección de recursos de la siguiente manera:
   ```yaml
   apiVersion: v1
   kind: Pod
   metadata:
     name: errorapp
     namespace: dev
     labels:
       app: errorapp
   spec:
     containers:
     - name: errorapp
       image: "nginx:latest"
       resources:
         limits:
           cpu: 250m
           memory: 100Mi   # Ajustado al límite máximo de la cuota
         requests:
           cpu: 250m
           memory: 50Mi    # Ajustado (50Mi es menor que la cuota de 100Mi)
   ```

2. Aplicar el Pod corregido:
   ```bash
   kubectl apply -f pod-quota-dev.yaml
   ```
* **Resultado esperado:**
  ```text
  pod/errorapp created
  ```

### Paso 7: Comprobar el consumo actualizado de la cuota
Volver a revisar la cuota para observar la actualización del consumo:
```bash
kubectl describe quota dev-quota
```
* **Aspectos a observar:**
  En la columna **Used** se debe reflejar el consumo actualizado de los recursos: `pods: 1`, `requests.cpu: 250m` y `requests.memory: 50Mi`.

### Paso 8: Limpieza de la Parte 1
Antes de pasar a la sección de límites por contenedor, eliminar los recursos de prueba creados:
```bash
kubectl delete quota dev-quota
kubectl delete pod errorapp
```

## Parte 2: LimitRange (Reglas para contenedores individuales)

Si un Pod se crea sin especificar los límites de CPU y memoria, este podría consumir una cantidad desmedida de recursos del clúster. Un **LimitRange** soluciona este escenario al asignar valores predeterminados y restringir las solicitudes mínimas y máximas permitidas.

### Paso 9: Crear el archivo de límites (`limitrange.yaml`)
Crear un archivo llamado `limitrange.yaml` con el siguiente contenido:

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: devlimits
  namespace: dev
spec:
  limits:
    - type: Container
      # Valores asignados por defecto si el contenedor no define recursos:
      default:
        cpu: 200m
        memory: 512Mi
      defaultRequest:
        cpu: 100m
        memory: 256Mi
      
      # Ningún contenedor puede superar estos límites máximos:
      max:
        cpu: 500m
        memory: 1024Mi
      
      # Ningún contenedor puede pedir menos de estos límites mínimos:
      min:
        cpu: 100m
        memory: 100Mi
```

### Paso 10: Aplicar el LimitRange
```bash
kubectl apply -f limitrange.yaml
```
* **Resultado esperado:**
  ```text
  limitrange/devlimits created
  ```

### Paso 11: Inspeccionar el LimitRange
Verificar la correcta aplicación de las reglas:
```bash
kubectl describe limitrange devlimits
```

---

### Paso 12: Probar la asignación por defecto
Crear un Pod sin especificar la sección de `resources` (CPU o Memoria) para comprobar si Kubernetes asigna los límites predeterminados de forma automática.

1. Ejecutar un pod de prueba directamente desde la línea de comandos:
   ```bash
   kubectl run new-dev --image=nginx
   ```
2. Inspeccionar los detalles del Pod creado:
   ```bash
   kubectl describe pod new-dev
   ```
3. Localizar la sección **Containers** y posteriormente **Limits** / **Requests** en la salida del comando.
* **Resultado esperado:**
  Verificar la asignación automática de las siguientes líneas por parte de Kubernetes:
  ```text
    Limits:
      cpu:     200m
      memory:  512Mi
    Requests:
      cpu:     100m
      memory:  256Mi
  ```

> [!NOTE]
> **Explicación:** El LimitRange asignó la configuración predeterminada al Pod de forma automática al omitirse en la definición.

---

### Paso 13: Probar la restricción de límite mínimo (Caso de error)
Intentar aplicar un Pod que solicite menos memoria de la mínima requerida (`100Mi`).

1. Abrir el archivo `pod-quota-dev.yaml` y modificarlo para que la solicitud sea inferior al mínimo:
   ```yaml
   apiVersion: v1
   kind: Pod
   metadata:
     name: errorapp
     namespace: dev
   spec:
     containers:
     - name: errorapp
       image: "nginx:latest"
       resources:
         requests:
           cpu: 250m
           memory: 50Mi  # <--- La solicitud de 50Mi es inferior al mínimo de 100Mi requerido.
   ```
2. Intentar aplicar el Pod:
   ```bash
   kubectl apply -f pod-quota-dev.yaml
   ```
* **Resultado esperado (Error):**
  El comando debe fallar indicando el incumplimiento de la política de límite mínimo:
  ```text
  Error from server (Forbidden): error when creating "pod-quota-dev.yaml": pods "errorapp" is forbidden: minimum memory usage per Container is 100Mi, but request is 50Mi
  ```

---

### Paso 14: Corregir y volver a aplicar
Ajustar la memoria del Pod para cumplir con el mínimo establecido en el LimitRange.

1. Modificar `pod-quota-dev.yaml` cambiando el valor de `requests.memory` a `100Mi`:
   ```yaml
         requests:
           cpu: 250m
           memory: 100Mi  # Ajustado al mínimo permitido
   ```
2. Aplicar el archivo:
   ```bash
   kubectl apply -f pod-quota-dev.yaml
   ```
* **Resultado esperado:**
  ```text
  pod/errorapp created
  ```

---

## Paso 15: Limpieza general del entorno

Al finalizar las pruebas, es necesario realizar la limpieza de los recursos creados.

1. **Eliminar el LimitRange y el Pod de prueba:**
   ```bash
   kubectl delete limitrange devlimits
   ```

2. **Eliminar todos los recursos del namespace `dev`:**
   ```bash
   kubectl delete all --all
   ```

3. **Restaurar el namespace por defecto en el contexto actual:**
   ```bash
   # Si se dispone de kubens:
   kubens default

   # O usando kubectl:
   kubectl config set-context --current --namespace=default
   ```

---

## 🎯 Resumen de aprendizaje
* **ResourceQuota** define límites agregados para todo el namespace (presupuesto grupal). Si los Pods combinados superan este límite, no es posible crear más Pods.
* **LimitRange** establece valores predeterminados y restricciones de rango (mínimos y máximos) para cada contenedor de forma individual.
* Ambas herramientas son esenciales en entornos de producción para evitar que un fallo de configuración o de desarrollo agote los recursos del clúster.
