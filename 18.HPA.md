# 1. Verificar Prerrequisitos (Metrics Server)

> [Instalación Metrics Server](https://github.com/kubernetes-sigs/metrics-server?tab=readme-ov-file#installation)

El **Horizontal Pod Autoscaler (HPA)** ajusta automáticamente el número de réplicas de un objeto de carga de trabajo (Deployment o ReplicaSet) según las métricas recolectadas de la aplicación.

Para que HPA funcione, el clúster debe contar con el complemento **Metrics Server** activo.

## 1.1. Verificar si Metrics Server está corriendo
```sh
kubectl get pods -n kube-system -l k8s-app=metrics-server
```

> Si no obtienes respuesta o el pod no está presente en Kind/MicroK8s, puedes instalarlo aplicando:

```sh
# Para el caso de Kind local sin TLS
kubectl apply -f /home/kube/kubelabs/assets/kind-hpa-components/components.yaml

# Para el caso con TLS
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
```

> Nota en Kind: Si el pod de Metrics Server falla por certificados TLS, puedes editar el deployment agregando la bandera `--kubelet-insecure-tls` en `spec.template.spec.containers[0].args`.

## 1.2. Validar lectura de métricas
```sh
kubectl top nodes
kubectl top pods -n kube-system
```
> Resultado esperado: muestra el consumo actual de CPU (`cores`) y memoria (`bytes`).


# 2. Crear Namespace `hpa-demo`

Toda la práctica se desarrollará dentro del namespace **`hpa-demo`**.

```sh
kubectl create namespace hpa-demo
```

> Opcional: Cambiar el contexto por defecto a `hpa-demo` usando `kubens`:
```sh
kubens hpa-demo
```


# 3. Crear Deployment con Definición de Recursos

> [!IMPORTANT]
> **Requisito Fundamental:** HPA utiliza los `resources.requests` especificados en los contenedores del Pod para calcular los porcentajes de consumo objetivo. Si no se configuran los `requests`, HPA no podrá calcular la utilización en porcentaje (`<unknown>`).

Crear el archivo `hpa-deploy.yaml`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: hpa-demo-deploy
  namespace: hpa-demo
  labels:
    app: hpa-demo
spec:
  replicas: 2
  selector:
    matchLabels:
      app: hpa-demo
  template:
    metadata:
      labels:
        app: hpa-demo
    spec:
      containers:
        - name: kubelabs-app
          image: cachac/kubelabs:3.0
          ports:
            - containerPort: 8080
          resources:
            requests:
              cpu: 50m
              memory: 64Mi
            limits:
              cpu: 200m
              memory: 128Mi
```

Aplicar el manifiesto:
```sh
kubectl apply -f hpa-deploy.yaml
```

Validar la creación de los pods en el namespace `hpa-demo`:
```sh
kubectl get pods -n hpa-demo -l app=hpa-demo
```


# 4. Crear el Service (ClusterIP)

Crear el archivo `hpa-svc.yaml` para exponer la aplicación:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: hpa-demo-svc
  namespace: hpa-demo
spec:
  type: ClusterIP
  selector:
    app: hpa-demo
  ports:
    - protocol: TCP
      port: 80
      targetPort: 8080
```

Aplicar el Service:
```sh
kubectl apply -f hpa-svc.yaml
```


# 5. Configurar HPA (Nivel Intermedio - API `autoscaling/v2`)

A diferencia de la creación imperativa mediante `kubectl autoscale`, la versión **v2** de HPA permite definir múltiples métricas (CPU y Memoria) así como **Políticas de Escalado (`behavior`)** personalizadas para controlar la velocidad de incremento (*scaleUp*) y reducción (*scaleDown*).

Crear el archivo `hpa-v2.yaml`:

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: hpa-demo
  namespace: hpa-demo
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: hpa-demo-deploy
  minReplicas: 2
  maxReplicas: 8
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 50
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 75
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0
      policies:
        - type: Percent
          value: 100
          periodSeconds: 15
    scaleDown:
      stabilizationWindowSeconds: 60
      policies:
        - type: Percent
          value: 50
          periodSeconds: 15
```

> **Explicación del `behavior` (Políticas de Escalado):**
> - `scaleUp.stabilizationWindowSeconds: 0`: Reacciona inmediatamente ante picos de tráfico subiendo réplicas sin esperar.
> - `scaleDown.stabilizationWindowSeconds: 60`: Espera 60 segundos de bajo consumo antes de desescalar para evitar oscilaciones rápidas (*flapping*).

Aplicar el HPA:
```sh
kubectl apply -f hpa-v2.yaml
```

Validar el estado del HPA en el namespace `hpa-demo`:
```sh
kubectl get hpa hpa-demo -n hpa-demo
```
Resultado:
~~~~
NAME       REFERENCE                  TARGETS           MINPODS   MAXPODS   REPLICAS   AGE
hpa-demo   Deployment/hpa-demo-deploy   0%/75%, 1%/50%    2         8         2          30s
~~~~

> Observa cómo HPA reporta los porcentajes actuales vs los objetivos para cada métrica definida.


# 6. Generar Carga para Probar el Autoescalado

Para simular tráfico entrante constante y elevar el uso de CPU, ejecutaremos un pod temporal en el namespace `hpa-demo` con un bucle de peticiones HTTP:

```sh
kubectl run load-generator -n hpa-demo --image=busybox:1.36 --restart=Never -- /bin/sh -c "while true; do wget -q -O- http://hpa-demo-svc.hpa-demo.svc.cluster.local; done"
```

En ventanas de terminal secundarias o mediante `watch`, monitorear la evolución del consumo y réplicas:

```sh
kubectl get hpa hpa-demo -n hpa-demo -w
```
o
```sh
kubectl top pods -n hpa-demo -l app=hpa-demo
```


# 7. Observar el Escalado Automático (Scale-Up)

A medida que el pod `load-generator` satura las solicitudes, el uso medio de CPU superará el umbral objetivo del 50%.

Resultado en `kubectl get hpa -n hpa-demo`:
~~~~
NAME       REFERENCE                  TARGETS            MINPODS   MAXPODS   REPLICAS   AGE
hpa-demo   Deployment/hpa-demo-deploy   85%/50%, 15%/75%   2         8         4          2m
hpa-demo   Deployment/hpa-demo-deploy   120%/50%, 18%/75%  2         8         8          3m
~~~~

Verificar el nuevo número de pods desplegados en el namespace:
```sh
kubectl get pods -n hpa-demo -l app=hpa-demo
```

Describir los eventos generados por HPA:
```sh
kubectl describe hpa hpa-demo -n hpa-demo
```
> En la sección **Events**, se registran los eventos de escalado como `SuccessfulRescale`:
> `New size: 4; reason: cpu resource utilization above target`
> `New size: 8; reason: cpu resource utilization above target`


# 8. Detener Carga y Observar el Desescalado (Scale-Down)

Eliminar el pod generador de carga del namespace `hpa-demo`:
```sh
kubectl delete pod load-generator -n hpa-demo
```

Monitorear cómo disminuye la utilización:
```sh
kubectl get hpa hpa-demo -n hpa-demo -w
```

> Gracias a la regla `scaleDown.stabilizationWindowSeconds: 60`, el controlador esperará un minuto en consumo bajo antes de reducir progresivamente las réplicas hasta retornar a `minReplicas: 2`.


# 9. Limpiar Recursos

```sh
kubectl delete -f hpa-v2.yaml
kubectl delete -f hpa-svc.yaml
kubectl delete -f hpa-deploy.yaml
```


# 10. Práctica de Repaso (Nivel Intermedio en Namespace `hpa-demo`)

## 10.1. Limpieza de recursos en el namespace `hpa-demo`
```sh
kubectl delete all --all -n hpa-demo
```

## 10.2. Crear el Deployment `store-api`
- **Namespace:** `hpa-demo`
- **Nombre:** `store-api-deploy`
- **Imagen:** Crear un index.html, contenerizar en una imagen con el nombre `[DOCKERHUB_STUDENT_ACCOUNT]/kubelabs-hpa:1.0.0`
- **Replicas iniciales:** 1
- **Puerto del contenedor:** 80
- **Recursos requeridos:**
  - `requests`: CPU 40m, Memoria 32Mi
  - `limits`: CPU 150m, Memoria 64Mi

## 10.3. Crear el Service `store-api-svc`
- **Namespace:** `hpa-demo`
- **Nombre:** `store-api-svc`
- **Tipo:** ClusterIP
- Exponer el puerto 80 hacia el puerto 80 del contenedor.

## 10.4. Configurar el HPA `store-api-hpa`
- **Namespace:** `hpa-demo`
- **API Version:** `autoscaling/v2`
- **Min Replicas:** 2
- **Max Replicas:** 6
- **Métrica:** CPU al 40% de utilización promedio.
- **Comportamiento (Behavior):**
  - Configurar un `scaleDown` con una ventana de estabilización (`stabilizationWindowSeconds`) de **120 segundos**.
- **Ajustar** los `request` para que los pods se estabilicen y reacciones adecuadamente al `HPA`

## 10.5. Checkpoint y Validación
1. Aplicar todos los manifiestos YAML asignados al namespace `hpa-demo`.
2. Ejecutar `kubectl get hpa store-api-hpa -n hpa-demo` y confirmar que muestre `TARGETS` en porcentaje (no `<unknown>`).
3. Generar carga al servicio con un pod `busybox` en el namespace `hpa-demo`.
4. Validar que las réplicas se incrementen de 2 hasta un máximo de 6 pods.
5. Detener la carga y comprobar que el desescalado tome al menos 120 segundos en iniciar.
